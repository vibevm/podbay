# PodBay

read [POST-MVP-CAMPAIGN.md](POST-MVP-CAMPAIGN.md) in full. It records the
owner-deferred phases, dependencies, acceptance gates, and the boundary that
lets Zap and VibeVM proceed without waiting for remote or cross-platform work.
Read [BACKLOG.md](BACKLOG.md) for evidence-backed owner decisions surfaced by
local dogfooding.
The [local MVP receipt](LOCAL-MVP-RECEIPT.md) records the tested PodBay → Zap
→ VibeVM cutover and its remaining operational limits.

PodBay is an independent Rust project for supervising arbitrary processes and their resources. Its design includes a distributed supervisor: a local pod owns process and PTY lifetime, while a future multi-host control plane routes guarded commands and observations across computers within PodBay itself. Agent providers such as Codex are adapters on that process foundation. Zap consumes PodBay's public contract and does not own the supervised processes. Coordinator, worker, and advisor are roles in one session/run/attempt/pod model.

Preproduction `0.1.0` has a versioned Rust wire contract, generated TypeScript binding, authenticated local Unix-socket transport, a durable command/event/outbox store, host authority, and Linux user-systemd pods. A private trusted manager policy and one-use setup socket enroll the exact launcher process and its process-owned Ed25519 key before enabling authenticated root Coordinator/Service launch and first `session.send`. The manager returns committed PodBay IDs and a current writer guard; `commands.get` reads the original command, current guard, and pod-journal evidence without repeating native input. `snapshot.get` reads a bounded current-scope projection with one event watermark rather than replaying historical commands. A fresh store is created directly at schema v24; older schemas are refused without migration. The authenticated `session.writerLease.renew` command atomically extends an unexpired exact lease with a durable same-key receipt; Zap must still schedule this command before expiry.

Disposable native tests prove one fake app-server turn through Node → Rust manager → pod, same-key replay without a second turn, and a real local `gpt-6-sol`/medium turn through the host path reaching fsynced `BootstrapCompleted` after a matching completion notification and fresh idle read. The later-turn path commits an exact intent, claims it once, and reads pod-journal evidence through `commands.get`; a real Zap smoke completes a second Codex turn without resending its duplicate. Native fixtures also prove a second fake turn after A→B rebind and a lost reply that remains uncertain without another input frame. Short encoded `turn/start` frames up to 512 bytes advance without blocking pod status; longer frames use the checked synchronous path and can block status during the native RPC. After owner recovery, Linux manager startup reads current V2 Pods in indexed pages of at most 128 and requires proof-bearing rebind plus an exact writer-lease takeover for every candidate before opening `manager.sock`. A later-page failure reports how many Pods were settled and leaves the manager unready. A two-Node-process fixture proves that a SIGKILLed manager leaves its V2 pod and Codex child alive: the new manager rebinds the same processes and sends one fenced first turn without relaunch or duplicate input. An opt-in Linux pidfd watcher now ties the manager to its exact direct launcher; a disposable headless Zap fixture proves that SIGKILLing Node makes the old manager exit autonomously, then a new Node recovers the same Pod and child with one native turn. Changed policy or a missing pod keeps the manager unready. Codex HOME and command/event journals are private per manifest slot. A pod-local native event snapshot and bounded redacted replay exist. Authenticated `native.events.read` admits verified Codex V2 frames to a private v24 store table and replays them by an exact Resource cursor; raw JSONL is returned only to the current owner actor with its scoped send grant.

An operator-installed Linux `operator_process_v1` profile can also launch one exact generic Service executable and argument vector in a pod-owned systemd unit. A disposable native fixture launches the real headless Zap server, verifies its authenticated empty-workspace setup response, reads back the original durable launch receipt on duplicate, and checks the direct child PID and birth. A two-manager fixture then proves that the same Zap child and its authenticated HTTP session survive A→B rebind without relaunch. This outer operator resource has no provider turn API of its own; Zap uses a separate inner PodBay manager for its coordinator. The installed operator CLI now pins a complete private Zap artifact, supports signed same-key launch/rebind and exact stop, and permits a reviewed Coordinator/Service to run UntilStopped without RuntimeMaxSec. A disposable nested fixture proves one fake Codex turn and output/ACK across outer A→B rebind, then exact unit cleanup. Recovery from another manager crash midway through generic rebind is not yet proven, and the outer startup output file is diagnostic evidence rather than a durable event cursor. See [the installed operator contract](crates/podbay-cli/OPERATOR-ZAP.md).

The local Zap source path now consumes authenticated native output with a durable ACK cursor, attests bootstrap completion before ready, and settles later turns only from pod-journal native_settled; a disposable fake-Codex Workspace test proves one explicit final_answer becomes one chat reply. A live VibeVM Zap cutover is under validation with one PodBay-rooted coordinator; final campaign acceptance remains separate. Delegated child-worker admission, repeated manager-crash recovery during rebind, and remote execution are outside the local MVP or unfinished. Linux Codex V2 slots use four bounded 8 MiB native event segments, a durable checkpoint and a 4096-event indexed tail; each private native frame is bounded at 4 MiB and authenticated local wire frames at 16 MiB. The former single-file native event format is refused; no migration path is maintained. Cached privileged reads verify new bytes and requested frames rather than replaying the lifetime log, although current host preflight still rechecks the executable and store on every call. Existing PTY and viewer slices are not connected to the Codex V2 path.

PodBay must support Linux, macOS, and Windows through one public API and separate OS backends. Current native runtime evidence is Linux-only. macOS and Windows do not yet have native acceptance receipts and must not be advertised as operational. The distributed supervisor is a PodBay capability, not a separate product, but remote launch and control are not implemented: the tested Linux path uses local user-systemd and Unix sockets. `hostId` identifies a reviewed local target; it is not a remote transport. See [platform backends](vibevm/vibespecs/PROP-008-platform-backends.xml) and the [native protocol](vibevm/vibespecs/PROP-002-protocol.xml).

`vibe install --offline --registry <local-registry>` materializes the pinned package closure. `vibe validate` and focused Cargo tests verify the current package and code slices. The optional outward ACP gateway has not been implemented or certified.
