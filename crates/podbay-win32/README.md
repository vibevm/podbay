# podbay-win32 (PB27a–e)

This preproduction crate is the narrow Win32 FFI facade for PodBay's future Windows backend and is a member of the root Cargo workspace. It does not implement manifest reconciliation or a complete `SupervisorBackend`.

`launch_independent_suspended` creates an explicit absolute executable with an empty Unicode environment and no inherited handles. The caller supplies an already normalized Windows command line; this facade does not quote arguments or infer shell semantics. It requires the new pod process to be outside **all** Job Objects before exposing a resume method. A restrictive parent Job Object therefore produces a typed refusal while user code remains suspended. The caller must durably admit the PodBay command/manifest first and must not retry an uncertain creation outcome. Closing a `RunningProcess` observation handle does not kill an independent pod.

The empty environment is an intentional credential boundary for this slice and may make some executables unusable. A later PodBay launch policy must provide an explicit reviewed environment block; ambient manager variables are never inherited by default.

Inside the attested pod, `PodJob::new_in_pod` creates an unnamed Job Object with `KILL_ON_JOB_CLOSE`; no job handle is exported to the manager or worker. `spawn_child` creates a child suspended, assigns it to that job, verifies membership, then resumes its primary thread. On refusal, the suspended-process guard terminates and waits up to five seconds before returning a clean `Unsupported`. If termination or the wait fails, it returns `UncertainAfterCreate` with the available process identity; a suspended orphan may remain. Native fault-injection tests are required before claiming complete cleanup.

Process identity is PID **plus** `GetProcessTimes` creation time. `open_exact_process` only pins that OS identity; it does not authorize PodBay reattachment by itself. The future backend must also verify the manifest digest, PodId/AttemptId/incarnation, scoped pipe principal, and credential generation.

PB27b adds `PodJob::spawn_conpty_child`. It dynamically resolves ConPTY exports before creating pipes, so an unavailable ConPTY returns `Unsupported` instead of preventing the binary from loading. It binds a pseudoconsole through `STARTUPINFOEX`, creates the child suspended, then uses the PB27a Job assignment fence before resume. Anonymous non-inheritable input/output pipes stay private to the pod. Separate output, input, and control threads keep output draining during writes, resize, and `ClosePseudoConsole`. Methods bound input size, geometry, page size, and call deadlines. A timeout or partial input write is `Uncertain` and permanently fences further input on that object; it is never evidence of application consumption. `close(&mut self, ...)` leaves the object available to read final output while the reader drains.

The PB27b output ring is **memory only**, bounded to 1 MiB/256 chunks with an explicit gap and `partial=true`; it has no durable spool or terminal-screen parser checkpoint. PB27c pipe viewer grants are separate and are not yet wired to the output ring. `close` completion proves only that the ConPTY close call returned, not that the child exited or work succeeded. A native Windows fixture must verify handle lifetimes, ConPTY close under output pressure, child Job containment, and the timeout/fault paths before this backend is usable.

PB27c adds one-shot local pipe control. The server uses an explicit protected DACL for the current logon SID and System, `FILE_FLAG_FIRST_PIPE_INSTANCE`, one instance, and `PIPE_REJECT_REMOTE_CLIENTS`. The logon ACE grants data read/write and synchronize, **not** instance creation. The default Everyone-readable pipe DACL is never used. Both sides pin the peer process and compare PID **plus creation time** before a capability is sent or a request is returned. Server-side `PeerGrant` checks exact pod/incarnation/generation and a separate viewer or controller token; a viewer cannot return an input/resize request to the dispatcher. Tokens and payloads are redacted from `PipeRequest` debug output.

PB27c establishes a one-shot transport: after one accept or timeout that instance is consumed. Pipe frames are capped at 64 KiB and each public accept/exchange/response call has a deadline of at most five seconds. A same-account sibling with a stolen token is refused by registered process-birth mismatch in the code path, but this has no native adversarial receipt yet. Danger-full-access agents sharing one account still require an external isolation boundary for strong hostile-peer security.

PB27e replaces the unbounded blocking worker with overlapped accept/read/write. Every request owns a stable `OVERLAPPED`, manual-reset event, buffer and pipe handle until completion. A deadline requests targeted `CancelIoEx`; only `GetOverlappedResult` proves whether it completed, canceled, or remains pending. Still-pending cancellation moves the whole request to a capped 32-slot quarantine, with no blocked worker thread and no dangling kernel buffer; later calls reap completed entries. If cancellation never completes, that slot remains reserved until process exit and new requests eventually refuse at the cap. Timeout races remain `Uncertain` and never dispatch an effect. The pipe service is **still one-shot**; multi-instance read-only viewers and a separate controller endpoint require a later native gate.

PB27d adds an NTFS-only durable-file slice. It creates a new local directory and logs with an explicit current-logon/System DACL, refuses reparse paths, checks directory/file volume serials, and requires NTFS persistent ACLs. A checksum-framed append returns a typed `FlushReceipt` only after `FlushFileBuffers` succeeds; its evidence is explicitly `ProvisionalNtfsFlush`, not production power-loss proof. A failed or ambiguous write/flush latches this `DurableDirectory` uncertain, so later input cannot be marked settled through it. A checkpoint is an immutable generation file flushed before a separate checksummed commit record is appended and flushed; recovery trusts only the latest complete referenced generation. Mutable reopen also checks that this generation is intact and its watermark is present in the event log. Torn commit tails, missing or changed generations, and event gaps are `Unknown`, never silently replaced by an older screen. Orphan uncommitted generations are ignored.

No `ReplaceFileW` or POSIX rename durability is assumed. The volume check uses Windows volume-serial evidence and explicit reparse checks, but hostile same-account path substitution and ACL drift on reopen are not a proven isolation boundary. NTFS power-loss, directory-entry persistence, ACL/reparse race, disk-full and wrong-volume behavior still require native fault-injection receipts before this facade can issue production durability claims.

The public Rust entry points are safe; the only unsafe calls are documented in `src/windows.rs`. `windows-sys` owns the raw Win32 bindings. A Windows runner must prove manager-job breakaway, survival across manager restart, Job Object descendant cleanup, error/fault paths and process birth identity. Cross-target compilation is not that proof. The overall backend design and references are in `/fast/git/v/research/2026-10-03-podbay-windows-backend.md`.
